# 工程规范

本项目遵循以下规范. 本文件由 project-navigator 在规范对照后写入; 需要修改时, 在编排会话中重新做规范对照.

## 架构与模块化

1. 修改前先读取项目相关代码, 文档, 配置, 测试和局部规则. 优先遵循既有架构, 目录结构, 模式, 命名和技术栈.
2. 默认按职责或功能划分物理目录, 形成清晰的模块边界. Visual Studio 项目例外: 源码物理目录保持扁平, 通过项目筛选器表达模块边界.
3. 每个文件, 模块, 函数和类等等只承担一个清晰职责. 模块必须高内聚, 低耦合, 通过明确接口通信, 可独立理解和测试.
4. 优先复用已有实现. 出现真实重复时再提取共享单元, 不为假想复用过早抽象.
5. 常量, 类型, 配置, 规则, schema 和业务知识必须保持单一数据源.
6. 分离表现层, 业务层和数据层. 跨层只能通过明确接口交互.
7. 依赖稳定抽象. 在替换实现或测试需要时, 通过适配层隔离框架, 数据库, 第三方服务和外部细节.
8. 优先组合而非继承. 同类问题采用一致结构, 消除循环依赖, 魔法数字和魔法字符串.
9. 严格执行 YAGNI. 不增加未请求功能, 兼容路径, 扩展点或无关重构.
10. 难以测试是职责不清或耦合过高的设计信号, 应先改善模块边界和接口设计.

## 模块粒度

1. 模块粒度宁细勿粗: 按职责拆到足够细, 让未来新增功能主要以新增模块接入, 而不是改动已有模块的内部实现. 拆细是刻意的取舍.
2. 细分模块与 YAGNI 不冲突: YAGNI 限制的是未请求的功能, 兼容路径与扩展点, 不限制按职责细分.
3. 粒度随项目灵活调整, 判断标准是 "一个模块只承担一件事".
4. 验收时检查: 本次新功能是否迫使多个已有模块改动内部实现. 如果是, 说明模块粒度不够.

## 代码质量与注释

1. 所有声明性代码元素必须具有完整的语言标准文档注释, 包括类型, 类, 接口, 结构体, 枚举, 常量, 字段, 全局变量, 函数和方法.
2. 支持 Doxygen 的语言使用标准 Doxygen 多行块注释. 不得使用单行注释充当声明文档.
3. 其他语言使用社区标准文档注释格式.
4. 函数或方法体内部不得写注释. 必须通过清晰命名, 结构和职责拆分表达逻辑.
5. 使用项目既有的命名, 导入, 类型, 错误处理和代码风格规范.
6. 保留批准范围外的用户改动和既有行为. 未经授权不得清理, 还原, 移动, 覆盖或删除用户内容.
7. 对删除, migration, cleanup, 外部写入或其他难以恢复的操作, 必须先确认精确目标, 影响范围和恢复路径. 缺少明确授权时不得执行.

## 技术选型

1. 技术选型必须遵循以下优先顺序:
   - 已安装且符合需求的现有技术栈, 库, 组件和工具.
   - 项目既有但尚未使用的成熟能力.
   - 安全, 可靠, 稳定, 高效, 活跃且符合生产级最佳实践的第三方库.
   - 仅在不存在合适成熟方案时, 才自行实现必要能力.
2. 不得在存在合适成熟库时重复造轮子.
3. 不得为了轻量化, 包体积, 是否偏重, 版本锁定, 部分功能暂未使用或其他非质量因素, 放弃更成熟可靠的生产级方案并选择小众库.
4. 新增依赖时, 优先选择安全, 可靠, 稳定, 高效, 活跃, 长期维护且最适合当前项目的生产级库.
5. 已确定技术栈必须一致采用. 例如项目已使用 Shadcn 和 Tailwind CSS 时, UI 必须优先使用 Shadcn 与 Tailwind CSS, 禁止使用原生 UI 组件或引入其他 UI 框架.
6. 实现功能前先判断现有依赖能否完成需求. 现有依赖不具备能力时, 再选择符合生产级要求的第三方库.
7. 对不确定的库, 框架, SDK, API, CLI 或云服务行为, 先使用 Context7 查询准确版本和权威文档. Context7 不可用时查询官方文档.
8. 不混用无关的组件系统, 数据层, 测试框架, 状态管理方案或部署工具.
9. 选型必须准确: 用库的源代码核实它是否真的能达成需求, 不凭记忆回答. 每项关键能力都要附源码证据 (仓库地址, 版本或提交, 文件路径与行号); 只有文档或记忆作依据的说法视为未核实.

## 注释语言

代码注释使用中文.

## 项目约定

本节来自规范对照中用户的选择, 与上文冲突时以本节为准.

1. Prettier 风格以全局规则为准: 字符串用双引号, 语句带分号, 多行结构带尾随逗号, 行宽 80; 项目的 .prettierrc.yaml 随之改为这些取值, 并按此一次性重新格式化脚手架文件.
2. 函数或方法体内严格不写任何注释, 包括解释 "为什么" 的行内注释与待办注释; 不采用全局语言规范中允许行内注释的条款.
3. TypeScript 编译基线沿用项目既有 tsconfig: noImplicitAny 保持关闭, 模块解析使用 bundler.
4. 产物目录与 package.json 字段以项目现状为准: 构建产物保持在 out/, 不强加 dist/ 与 "type": "module".
5. 文档注释覆盖所有声明性代码; 形式上禁止用 // 或单行 /** */ 充当文档注释.
6. 文件过大意味着职责过多, 应及时拆分.
7. 最终质量门之前统一格式化改动文件; 涉及 Git 提交消息时必须使用生成提交消息的技能.
8. TypeScript 文件名用 kebab-case, 接口不加 I 前缀, 标识符禁缩写, 禁用 any 而用 unknown 并收窄, 导出函数显式标注返回类型, 枚举优先用字符串字面量联合或 as const, 优先命名导出, 类型导入用 import type, import 分组排列.
9. 注释中不重复签名里已有的类型信息.
10. 交流与注释一律使用 ASCII 标点, 每个标点后加一个空格; 读文件用 Read 工具, 创建与修改文件用 Write 与 Edit 工具.
11. 项目文件统一使用 lf 换行, 文件末尾保留空行, 去除行尾空白, 以 .editorconfig 与 .gitattributes 为准.
12. 工程结构沿用项目现状: tsconfig 拆成 node 与 web 两个 project references, 渲染进程路径别名为 @renderer/*, build 脚本先 typecheck 再构建.
